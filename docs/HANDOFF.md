# Handoff

## Current implementation

- Phase 1 foundation is implemented with Next.js App Router, TypeScript, Tailwind CSS 4, and a responsive dark navy/charcoal shell with restrained purple accents.
- Sidebar navigation works for Dashboard, Games, Analysis, Openings, Tactics, Calculation, Strategy, Endgames, OTB Training, Coach, and Progress. The not-yet-built sections explain their planned next feature rather than presenting fake activity.
- First visit displays onboarding. Profile name, current Lichess Classical rating (default 1800), weekly study hours, and preferred side are saved to the local SQLite database through Prisma. The goal defaults to Candidate Master / 2200 FIDE Standard.
- Dashboard reads the saved profile and labels rating/progress baseline. It does not claim invented streak or training statistics.
- Development startup generates Prisma Client and applies SQLite migrations. Production builds generate Prisma Client and leave SQLite untouched. The game viewer uses chess.js and react-chessboard.
- Games includes its interactive viewer plus PGN save/list/reopen controls backed by `/api/games`. API validates PGN, stores multi-game imports, and deduplicates by SHA-256 of normalized PGN using SQLite-compatible transactional upserts. ChessGame stores metadata, PGN, initial FEN, and optional unique fingerprint.

## Phase 3 — Lichess game integration

- In **Games → Lichess settings**, save a public username to load Classical, Rapid, and Blitz ratings. **Refresh ratings** updates the snapshot. The username and ratings persist in SQLite independently of onboarding.
- **Sync Games** defaults to 50 Classical games. The available limits are 10, 25, 50, and 100. Sync uses the official public profile and NDJSON game export endpoints with no credentials. It requests completed games only and streams imported, skipped, and failed counts to the page.
- The additive migration `202611180003_lichess_sync` adds the settings table and optional game ID, speed, and clock metadata. Imports retain the source PGN, tags, and clock comments when provided. Imported records appear in **Saved games** and open through the existing viewer.
- Repeat syncs check the latest bounded window for new IDs. The existing SHA-256 PGN fingerprint and official Lichess Site URLs also match saved manual exports. Existing records are preserved on a match.

## Phase 4A — Local Stockfish

- In **Games**, select a move or load a FEN, then click **Analyze position** below the board. Stockfish.js 19.0.1 Lite runs in a dedicated, single-threaded Web Worker. Default depth is 12, with depths 6–18 available. Analysis starts on demand for one position per tab.
- The UCI runner waits for `uciok` and `readyok`, reports depth progress, converts the best move and variation to SAN, and shows centipawn and mate scores from White’s perspective. Checkmate, stalemate, insufficient material, and the 75-move rule are detected from the position. Repetition and prior game adjudications require game history and are outside FEN-only analysis.
- Cancel, change positions, or leave Games to stop the worker. Analysis also stops after completion or a timeout. **Analyze again** runs a fresh search.
- Up to 64 completed results are cached in browser storage. The cache key includes the saved game ID when available, full FEN, Stockfish build, search settings, and requested depth. Results stay in the current browser profile. No database migration was needed.
- Development and production builds copy the pinned engine assets unchanged. The served notice names the authors and exact corresponding source. The full GPL v3 text is served alongside the worker. [Stockfish.js 19.0.1 release and source](https://github.com/nmrugg/stockfish.js/releases/tag/v19.0.1)

## Remaining limitations

- Sync runs on demand and covers the selected recent window. A repeat sync rechecks that window so failures can be retried. Games older than the selected limit are outside that run.
- A manual PGN with an edited fingerprint and no recognizable Lichess Site URL may remain a separate record. Missing ratings and clocks depend on public data availability.
- The request lock and rate limit cooldown are shared by the running local server process. After a restart, observe any previously reported retry delay before syncing.
- Full game review and training workflows remain pending.

### Phase 6B-2A — Persistent opening history and spaced repetition engine

- Added additive migration `202611190005_opening_spaced_repetition` with `OpeningTrainingPosition` and `OpeningTrainingReview`. Position schedule rows keep scalar repertoire/chapter references (no cascading deletion), position identity, side, starting/current FEN, exact SAN context path, saved expected UCI continuations, applicability, last/next dates, interval, repetition, ease, and recent grade history. Review records store the submitted move, first-attempt result, incorrect/hint/reveal counts, grade, timestamp, and a unique idempotency key.
- The position builder derives review choices from saved chapter PGNs with chess.js. It merges multiple acceptable saved continuations at the same contextual node and keeps White/Black separate. Identity hashes repertoire, chapter, color, starting FEN, current FEN, and exact prior SAN path; transpositions reached by different paths remain separate. Reconciliation updates expected moves and marks removed positions inapplicable while preserving their review history.
- Added transparent deterministic SM-2-inspired scheduling: unassisted first-try success grades 5; a hint lowers that to 3; a correct response after an incorrect attempt grades 2; a reveal or an incorrect final response grades 0. Grades below 3 reset repetitions and schedule in one day. Successful grades use 1 day, 6 days, then the rounded prior interval times the updated ease factor (minimum ease 1.3). Recent grades retain the last eight outcomes. Due selection exposes new, overdue, due-today, recently mastered (interval at least 21 days and not due), and repeatedly forgotten (last two grades below 3) positions.
- Added `GET/POST /api/openings/training`. GET reconciles saved branches, returns due/new/mastered/forgotten positions and aggregate counts by repertoire/chapter, and can retrieve an individual position's review history, including stale records by position identity. POST validates repertoire/chapter/color association, requires a current saved decision position, validates the submitted legal move and counters, derives correctness server-side, saves the schedule and review atomically, and rejects idempotency-key reuse across different positions. Duplicate request keys cannot create duplicate reviews.
